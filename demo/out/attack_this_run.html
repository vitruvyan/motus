The event log here is not a strawman: it carries a payload_hash on every row, which is the strongest thing such a table usually has, and it is credited with every catch it earns. It even catches the deletion — not by any digest, but because the row below the deleted one names it in causation_id, and that name now points at nothing. Repair that one field, which no hash covers, and the deletion becomes invisible. What the log has no value for is the set: no row commits to any other, so a rewritten header or a changed policy leaves nothing behind.

Read the resealed row twice. An attacker who knows the contract redoes every hash and passes both checks — the tampered trace is internally perfect. The one thing they cannot do is reach a root already published somewhere else. That row is the case for anchoring, and it is the only one the validator cannot win.

The last row is a different animal. The validator does catch it, but the raw terminal field still carries the published root — so anyone who compares that field to the anchor sees agreement. trace.root recomputes the whole chain from the document and answers None. That is why the root is an accessor and not a field you read.

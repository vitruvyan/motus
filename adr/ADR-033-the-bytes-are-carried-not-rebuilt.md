# ADR-033 — the bytes are carried, not rebuilt

- **Status:** ACCEPTED
- **Date:** 2026-09-07
- **Accepted:** 2026-09-07, by the founder, all ten decisions. The four hypotheses are accepted as hypotheses: H1 and H2 are tested before the first publication, H3 and H4 are falsifiable by the first run of the machinery they describe, and each names what this ADR is amended to say if it fails.
- **Authority:** CTO proposes; the founder accepts. ADR-032 decided *that* the open half ships on PyPI and left *how* to the workflow of PR #72. An adversarial round against that workflow on 2026-09-07 returned ten findings, three of which are unfixable inside the shape the workflow has. This ADR settles the shape. Nothing here reopens an ADR-032 decision.
- **Depends on:** ADR-032 (all eight decisions stand), ADR-006 (the version string is coupled to committed evidence), ADR-012 (a release states its own cost, and the gate is relative), ADR-020 §7 (the runtime ships an interface and never an anchor).
- **Amends:** **ADR-032 decision 2, its mechanism only** — *"the wheel and sdist that the release workflow uploads to PyPI are the same bytes attached to the GitHub Release"* is kept exactly, and decision 2 below says the one way it can be achieved, because the obvious way is measurably impossible. **ADR-032 decision 3, one clause added** — reservation by pending publisher is kept; decision 3 below adds that a publisher is matched on the *workflow filename*, which forces one publish workflow per distribution. **ADR-032 decision 4, made specific** — "the last step of the release act" acquires the two human steps it turns out to need. **ADR-032's hypothesis H1 is replaced** by H1 below: as written, H1 proposed to test the system by walking through the hole this ADR closes. No ADR-032 *decision* is amended, and decision 8 (public at first publication) is untouched.

## Context

**What PR #72 gets right, so that this ADR is not read as a rejection of it.** Trusted Publishing instead of a stored token; firing on the *published* release rather than the tag push; a gate that refuses a wheel whose version is not the tag; a smoke test that installs the built wheel into a clean interpreter, runs a graph, and makes the shipped validator refuse an edited trace. Every one of those survives into this ADR. The round attacked the version gate with eight `(__version__, tag)` pairs — including PEP 440 normalisation, a missing `v` prefix, a leading zero, pre-releases and local versions — and produced **zero false passes**, with the two brittle cases failing closed. The tamper gate was attacked four ways and is fail-closed on every path, including the control that matters most: re-serialising the trace with `json.dump` and changing nothing validates clean, so the gate is not passing merely because the bytes were reshaped. The `permissions:` blocks are tighter than most projects manage — the publishing job holds `id-token: write` and nothing else, not even `contents`.

**The finding that decides this ADR, because it is a measurement and not an opinion.** Two builds of the same tree, same interpreter, minutes apart:

```
build A: c9e17e82…  vitruvyan_motus-0.14.0-py3-none-any.whl
build B: 4691260d…  vitruvyan_motus-0.14.0-py3-none-any.whl
byte-identical: False        (the sdist differs too)
```

Zip member timestamps follow file mtimes, so a checkout produces a different archive every time. **A release note can therefore only name the hash of bytes it carries, not of bytes anyone can regenerate.** This kills the repair that everyone reaches for first — *rebuild from the tag and compare against the note* — and it is why ADR-032 decision 2 cannot be satisfied by a workflow that builds twice. It has to build once and carry the result.

**The publication path does not pass through anything that reviews it.** `main` has branch protection with three required checks, and `required_approving_review_count: 0`, `required_signatures: false`, `enforce_admins: false`. There is **no tag protection** (`/tags/protection` → 404) and **no ruleset** (`/rulesets` → `[]`). A release requires only a tag, anywhere, on any commit. So the protection that exists guards `main`, and publication does not go through `main`. The version gate closes the gap it was written for — wheel version equals tag — and does not close this one: it never checks that the tagged commit is the reviewed commit, that the suite passed on it, or that the evidence ADR-006 couples the version to (`benchmarks/relative-<X.Y.Z>/`, `benchmarks/candidate-v<X.Y.Z>-epyc-py310.json`) exists at all.

**`workflow_dispatch` is a publication path, and the workflow file is not a trust boundary.** The version gate is the only guarded step and its guard is `if: github.event_name == 'release'`, so a dispatch skips it. Worse than a missing check: GitHub runs the workflow definition *from the ref being dispatched*, so an attacker with write access to any branch does not need to satisfy the gates — they edit them out. Nothing compensates on either side. PyPI's warehouse puts `ref` and `sha` in `__required_unverifiable_claims__` and `ref_type`, `actor`, `repository_visibility`, `workflow_ref` in `__unchecked_claims__`; `_check_event_name` refuses only `pull_request_target` and explicitly allows `workflow_dispatch`. On the GitHub side, `actions/permissions` reports `allowed_actions: all`, `sha_pinning_required: false`, and `/environments` reports `total_count: 0` — **the `pypi` environment named in the workflow does not exist**, so the key buys nothing today. A dispatch from `main` right now would publish **0.14.0**, permanently consuming a version ADR-032 decision 1 says is not to be published.

**The environment protection everyone assumes is there is half-available.** Deployment *branch and tag* policies on a private repository need Pro/Team/Enterprise, which this account has (classic branch protection is active on a private repo). **Required reviewers and wait timers on a Free/Pro/Team plan are public-repository only.** So the window in which a human approval is most wanted — the first publication, and the tests of H1 — is exactly the window in which GitHub will not provide one. The approval has to be a human act outside Actions, or it does not exist. This is what decision 2 turns into an advantage rather than working around.

**Two facts about the artifact that are permanent per version.** `pyproject.toml` declares `readme = "README.md"`, so the README *is* the wheel's long description and PyPI renders it as the project page. Today's `main` builds a wheel whose METADATA contains four sentences that publication makes false, and `twine check` passes them (rc=0) because they are valid reStructuredText, not false statements it could know about. And `pyproject.toml` declares **no `[project.urls]` at all** — confirmed absent from the built METADATA — so the page of a product whose claim is *verification is always open* would carry no link to the repository, the contract or the licence. Both are unfixable after upload: PyPI does not allow a version to be re-uploaded, and the project front page renders the newest version's description.

**A fifth name, which decision 3 does not list.** README line 1098, `pyproject.toml` and ADR-009 all tell a reader that *"the `vitruvyan-axis` 0.4.0 distribution remains independently pinnable"*. `https://pypi.org/simple/vitruvyan-axis/` returns **404**. That sentence ships inside the METADATA and becomes a public instruction, next to a name anyone can claim, the moment the first wheel is uploaded. Checked the same day: `vitruvyan-motus`, `motus-console`, `motus-anchor-opentimestamps` and `motus-attest-rfc3161` are all 404; `motus` alone is taken.

**How a Trusted Publisher is matched, which determines how many workflow files there must be.** PyPI matches on `(owner, repository, workflow filename, environment)` and nothing else. Both plugs live in *this* repository. If all four names were registered against `publish-pypi.yml`, that one workflow would hold the right to publish under all four — the project is chosen by the uploaded file's metadata, and `twine upload dist/*` uploads whatever is in the directory — and the reservations would never be consumed, because that workflow only ever builds the root distribution. Correcting the filename afterwards means deleting and recreating the pending publisher: a window in which the name is claimable, which is the exact failure ADR-032 rewrote decision 3 to avoid.

## Decision

1. **No publishing workflow declares `workflow_dispatch`, and the version gate is unconditional.** The `release: [published]` trigger is the only entry. The gate loses its `if:` so that restoring a manual trigger later cannot silently skip it. Testing against the real index is decision 10.

2. **The bytes are carried, not rebuilt — the draft-release shape.** The release act becomes: tag → a **build** job on the tag builds the wheel and sdist once, runs every gate against them, attaches those exact files as assets to a **draft** GitHub Release, and writes their SHA-256 into the draft body → **the founder reads the draft and publishes it** → the `published` event fires a **publish** job that **downloads the release assets** and uploads those bytes, and does not build. This satisfies ADR-032 decision 2 literally: the same bytes are in both places because they are the same file, and the note names their hash because the hash was written before the note existed. It also supplies the human approval GitHub will not sell us while the repository is private (Context): publishing the draft *is* the approval, and it is made while looking at the artifact and its hash. `contents: write` belongs to the build job, which has no `id-token`; the publish job keeps `id-token: write` and nothing else. Draft releases do not fire `created`/`edited`/`deleted`, and publishing a draft does fire `published` — that asymmetry is what makes the shape work, and H2 below is how we find out if it stops being true.

3. **One publish workflow file per distribution**, named for what it publishes: `publish-motus.yml`, `publish-plugs.yml`, `publish-console.yml`. Each pending publisher is registered against its own filename. The files exist — as stubs if their first release is not authorised yet — **before** any pending publisher is registered, because a publisher cannot be re-pointed without releasing the name first.

4. **The `pypi` environment exists before any publisher is registered, and the publisher names it.** Creation order is: environment with a deployment **tag** policy `v*` → register the Trusted Publisher **with** environment `pypi` → first publication. Both halves are required and neither is sufficient: warehouse's `_check_environment` returns `True` when the configured environment is empty, and `_get_publisher_for_environment` falls back to the environment-less publisher, so a publisher registered with a blank Environment field is published to by a branch that simply deletes the `environment:` key.

5. **The build job binds the artifact to a reviewed commit and to committed evidence**, with `fetch-depth: 0`, `git merge-base --is-ancestor "$GITHUB_SHA" origin/main`, and the existence of `benchmarks/relative-<X.Y.Z>/` and `benchmarks/candidate-v<X.Y.Z>-epyc-py310.json`. This is the check the version gate was mistaken for. Note that the evidence directory naming is itself inconsistent — `relative-v0.7.0`, then `relative-0.8.0` onwards — so this check is clean from 0.8.0 and would refuse 0.7.0; that is acceptable because 0.7.0 is not being published.

6. **A metadata gate refuses a distribution whose long description contains a claim publication makes false.** It reads the built wheel's `METADATA` with `zipfile` and `email.parser` — the parsers that exist for those formats — and not a regular expression over `README.md`, because the question is about what *shipped* and the wheel is the only thing that can answer it. The list of forbidden claims is the frozen set recorded with this ADR; a thirteenth site added later fails the gate rather than reaching the index. `[project.urls]` is added in the same change, so the page carries the repository, the contract and the licence.

7. **Everything in the publishing path is pinned, including the environment that writes the bytes.** All actions by commit SHA, matching the convention the rest of `.github/workflows/` already follows and which `publish-pypi.yml` is the only file to break. `build`, `twine` and `[build-system] requires` are pinned and hash-checked from a committed constraints file, because `constraints/test.txt` states this repository's own rule — *"Ranges in pyproject declare intent; THIS file records the versions actually resolved… Regenerating it is a deliberate act recorded in a commit, never a side effect"* — and today it is applied to the environment that runs the tests and not to the environment that produces the artifact strangers install. One honest limit: `pypa/gh-action-pypi-publish` resolves to a GHCR *tag* even when pinned by SHA, so the pin's integrity is bounded by tag immutability at the registry, not by the pin. It is still strictly better than `@release/v1`, whose branch head moved on 2026-07-28.

8. **One publication at a time, and a re-run cannot change the bytes.** `concurrency: { group: publish-<distribution>, cancel-in-progress: false }`, and `skip-existing: true` on the upload. Without both, a transient failure between the wheel and the sdist is unrecoverable: shell glob order uploads the wheel first, "Re-run all jobs" rebuilds different bytes (Context), PyPI answers 400 *File already exists*, and the version is permanently wheel-only with no manual path, because the design deliberately stores no token. Decision 2 removes most of this by not rebuilding at all; `skip-existing` covers the remainder, and its cost is stated in *Consequences*.

9. **`vitruvyan-axis` is reserved as a fifth pending publisher**, or the three documents that call it *independently pinnable* are corrected to name the tag `v0.6.1` and `vitruvyan_motus.compat` instead. The first is cheaper and is the recommendation; either closes it, and leaving it open is not an option once the METADATA carrying that sentence is public.

10. **Attestations are declared, not defaulted, and the first end-to-end test runs against TestPyPI.** `with: attestations: true` is written even though the action's current default is `'true'`, because ADR-032 decision 2 says they are *kept enabled* and a state the file does not assert is a state a moving dependency can change. The disclosure is accepted deliberately: a PEP 740 attestation is a Sigstore bundle whose Fulcio certificate carries the repository URI, the commit digest, the source ref, the workflow path and the run URL, and PyPI serves it publicly — so publishing attestations while the repository is private discloses those facts about a private repository. Under ADR-032 decision 8 the repository is public at first publication, so this is consistent; if that decision is ever revisited, this one is revisited with it. H1 is tested against **TestPyPI**, with its own workflow file and its own publisher, and never by dispatching a production workflow.

## Consequences

- **What is given up: the release stops being fully automatic.** The founder must open the draft and press publish, and that is a human step inside an act ADR-006 already calls *one act, not four*. It is accepted because it is the only approval available (Context: required reviewers are public-repository-only on this plan) and because it is made at the moment the artifact and its hash are on screen — which is more than a GitHub approval button would show.
- **What is given up: `skip-existing: true` hides a real signal.** It also masks *someone already published this version*, which is exactly the state decision 5's ancestor check has to catch instead. Named here so the next reader knows the trade was made knowingly and where the compensating check lives.
- **What is accepted: three more workflow files and a constraints file to maintain.** Decision 3 makes the count grow with distributions rather than with releases, and decision 7 adds a file that must be regenerated deliberately. The alternative is one file with the authority to publish every name we own.
- **What does not change.** ADR-032's eight decisions, the release gate (ADR-006), the three characterisations (ADR-012), the note that states the cost (ADR-018), and the `permissions:` discipline PR #72 already has right.

## Alternatives rejected

- **Rebuild from the tag and compare the hash against the note.** The first idea everyone has, and the measurement in *Context* kills it: two builds of the same tree differ. It is rejected on evidence, not on taste, and it is recorded here because it will be proposed again.
- **Keep `workflow_dispatch` and guard it with `if: github.event_name == 'release'` on the publish job.** Rejected because it treats the workflow file as a trust boundary, and a dispatch runs the file from the chosen ref. A guard an attacker can delete is not a guard.
- **One `publish-pypi.yml` for all four distributions, selecting by input.** Rejected twice over: an input selecting what to publish is a dispatch trigger by another name, and PyPI matches a publisher on the filename, so one file means one publisher holding four names.
- **Append the SHA-256 to the release note after publication.** Rejected: the note names the hash only after the fact, a reader in the interval sees none, and it puts `contents: write` into the job holding `id-token: write`.
- **A regular expression over `README.md` for the forbidden claims.** Rejected under the repository's standing rule. The question is what the *wheel* carries, the wheel has a parser, and a pattern over the source file answers a different question — it would pass a README fixed after the build and fail on a sentence quoted inside a code fence.
- **Wait for the repository to be public so that required reviewers become available, then automate the approval.** Rejected as an ordering: decision 8 makes the repository public *at* the first publication, so the first publication is precisely the one that cannot have the reviewer. Decision 2's draft is the approval, and it keeps working afterwards.

## Hypotheses, labelled

- **H1 (replaces ADR-032's H1).** Trusted Publishing can be proved end-to-end without publishing to the production index, by a separate workflow file and a separate publisher against **TestPyPI**. Falsified if TestPyPI's OIDC path diverges from PyPI's in a way that makes a green TestPyPI run uninformative about PyPI — in which case the first production publication is itself the test, and decision 2's draft step is the only thing standing between a mistake and an unrepeatable version number. ADR-032's H1 as written proposed to test by dispatching the production workflow; that is not a test, it is the hole.
- **H2.** The draft-release shape fires as described: a draft release publishes, `release: [published]` fires once, and the assets attached to the draft are downloadable by the publish job. Falsified if `published` does not fire for a draft that is published, or if asset download requires a permission the publish job must not hold — in which case the fallback is to attach the assets in a job that runs on the `published` event *before* the upload step in the same job, keeping "build once" but losing the founder's sight of the hash before approval, and this ADR is amended to say so.
- **H3.** The metadata gate of decision 6 has no false positives on the corrected documents. Falsified the first time it refuses a distribution whose METADATA is in fact honest — the frozen list is then too broad, and the fix is a narrower list and a note here saying which claim was ambiguous.
- **H4.** `--require-hashes` locks for the build environment (decision 7) can be produced for `build`, `twine` and the `[build-system]` requirements without a resolver fight. Falsified if any of the three cannot be locked completely, in which case the pin is version-only, stated as such, and the claim in decision 7 is weakened rather than left standing.

# ADR-032 — the open half ships on PyPI, the sold half through Vitruvyan's installer

- **Status:** ACCEPTED
- **Date:** 2026-09-07
- **Accepted:** 2026-09-07, by the founder, all eight decisions — including decision 8: the repository becomes public at the first publication. Three of the mechanisms written here were wrong when the text was proposed and were corrected in place before acceptance was recorded: what the wheel actually ships (*Context*), how a name is reserved on the index (decision 3), and the form a hash pin can take (decision 5). **No decision changed; three ways of carrying one out did.** The three were found by review on PR #161 and each was checked against the code or the index before the correction was written.
- **Authority:** CTO proposes; the founder accepts. Distribution is a public act (ADR-006 consequences, the `release` skill): nothing here is executed before acceptance.
- **Depends on:** ADR-006 (the version string is coupled to committed evidence), ADR-012 and ADR-018 (a release states its own cost), ADR-020 (levels 1–5 open, 6–7 sold; §7 concrete anchors are separate distributions), ADR-021 decision 8 (verification needs no Vitruvyan endpoint, key or company).
- **Amends:** **ADR-001, one first-commit condition** — *"No PyPI publication before the license decision and the name-migration plan are approved"* is a **condition, not a prohibition, and both its terms are met**: the licence is Apache-2.0 and the migration from `axis` to `vitruvyan-motus` is done and shipped through fourteen releases. It is named here because ADR-001 sits at the top of the authority order, so a reader who finds that line and not this one concludes that publication is forbidden. **ADR-006, one sentence** — *"No PyPI publication is authorized by this ADR"* is replaced by decision 1 below; the gate it describes is untouched and becomes a precondition of publication. `.claude/skills/release/SKILL.md` — the line *"Motus is not published to PyPI; do not"* becomes the publication step (decision 4). `README.md` — the two statements that Motus is not on PyPI (header and *Install for development*) become true install instructions on the day of the first publication and not before.

## Context

**What is distributed today.** `vitruvyan-motus` is installed from a git tag: Orbis pins `vitruvyan-motus @ git+https://github.com/vitruvyan/motus@v0.14.0`, Limen builds its image with `ARG MOTUS_TAG=v0.14.0`. The README says twice that the package is not on PyPI and that `pip install vitruvyan-motus` fails (the index answers 404 for the name, checked again on 2026-09-07; `motus` alone is taken, `motus-console`, `motus-attest-rfc3161` and `motus-anchor-opentimestamps` are free). The two plugs are installable only from the checkout. The GitHub Release carries the tag, the notes and the evidence, and no wheel.

**What already exists and was held.** PR #72 (2026-08-09) adds `.github/workflows/publish-pypi.yml`: Trusted Publishing (PyPI verifies the workflow's OIDC identity; no token is stored anywhere), fired on a *published* release and not on a tag push, with two gates before upload — the built version must equal the tag, and the wheel is installed into a clean interpreter, runs a graph, and the shipped validator is made to refuse an edited trace. It was held open because publication is a decision and not a chore, and because the README becomes the PyPI description while the repository is private.

**What the packaging tests already claim about the wheel.** `tests/test_motus_packaging.py` builds a real wheel and checks: it is named for the declared version; it ships the package, `py.typed`, and from `contract/` an **exact enumerated set of ten paths and no eleventh** — the validator (`validate.py`, `__init__.py`), five schemas (`trace.v1`, `graphspec.v1`, `checkpoint.v1`, `commitment.v1`, `receipt.v1`) and three prose documents (`README.md`, `guarantees.md`, `node-protocol.md`, which travel for ADR-022's reason: an MCP citation an agent cannot resolve after `pip install` is not a citation), while the 660 KB conformance corpus stays in the repository; **two** of those schemas, `trace.v1` and `graphspec.v1`, are additionally compared byte-for-byte with the tree, and the other three are not; it declares `jsonschema` and nothing else (the kernel imports only the standard library; the shipped validator needs `jsonschema` — two claims, both stated); the validator is exposed as the `motus-validate` command; installed alone, Motus imports and its predecessor does not. Publishing changes none of these; it makes them the claims a stranger relies on.

**Where the commercial line is.** ADR-020 §6: levels 1–5 are open and free because they are arithmetic; 6–7 are sold because an accredited party asserts something and carries liability. Perpetuum is the sold half. Limen is a private repository. The Continuum console (motus#160) shows the open half and nothing else.

**The founder's decision of 2026-09-07.** The open version — Motus and the Continuum console — is distributed through PyPI, the industry standard for Python software; the paid version through Vitruvyan's proprietary installer. Jenkins on `build.vitruvyan.com` serves `aicomsec` and `vitruvyan-core` and is not attached to Motus, Limen, Orbis or Vit; the `vitruvyan-packages` distribution is to be rethought for the new projects (vitruvyan-packages#1).

**One fact the decision has to face.** The repository is private. A PyPI project whose description links to a repository the reader cannot open, whose validator source the reader cannot read, and whose contract the reader cannot compare with the shipped schemas contradicts the property the whole product rests on: *verification is always open, at every level* (ADR-020 §6, ADR-021 decision 8). The wheel ships the validator and the schemas, so a reader *can* check a receipt without the repository. What they cannot do is check that the validator is what we say it is. That is a weaker position than the one we sell.

## Decision

1. **`vitruvyan-motus` is published on PyPI**, from the tag of each release, by the workflow of PR #72 through Trusted Publishing, under the PyPI organisation `vitruvyan` the founder creates with two-factor authentication. This replaces the sentence in ADR-006. No release before this ADR's acceptance is published retroactively; the first publication is the first release after acceptance (0.15.0 unless the founder says otherwise).

2. **One wheel, two places.** The wheel and sdist that the release workflow uploads to PyPI are the same bytes attached to the GitHub Release, and the release note names their SHA-256. A reader who holds one can check it against the other. The PEP 740 attestation Trusted Publishing produces is kept enabled; it is the provenance of our own artifact and it costs nothing. **Amended by ADR-033 (accepted 2026-09-07), decision 2: the mechanism is that the bytes are carried, not rebuilt, because the obvious alternative — rebuild from the tag and compare — is measurably impossible. Two builds of the same tree produced different archives (`c9e17e82…` vs `4691260d…`, and the sdist differed too), because zip member timestamps follow file mtimes; a release note can therefore only name the hash of bytes it carries, never of bytes anyone could regenerate. The bytes are attached to a draft GitHub Release and the publish job uploads what it downloads, and does not build.**

3. **The plugs and the console are separate distributions on the same index** — `motus-anchor-opentimestamps`, `motus-attest-rfc3161` (both `0.1.0` today) and, when it exists, `motus-console` (motus#160). This is ADR-020 §7 taken literally: the runtime ships an interface and never an anchor, and an index of independent distributions is the shape that says so. Each has its own version, its own packaging test and its own release note; none is published before its first release is authorised. The names are reserved on the index **before** the first publication of the runtime, by the mechanism the index actually offers: a **pending publisher** — a Trusted Publisher registered against a project name that does not exist yet, which PyPI then holds for that publisher until its first upload. Nothing is uploaded, nothing installs, and the name cannot be taken by anyone else in the meantime. The draft of this decision said a reserved name was *"an empty release with a note saying so"*: **PyPI has no such operation** — a release exists only by uploading distribution files — so that instruction would have left all three names claimable for exactly the interval it was written to protect. **Amended by ADR-033 (accepted 2026-09-07), one clause added to decision 3: PyPI matches a Trusted Publisher on `(owner, repository, workflow filename, environment)`, not on the project name alone, so one workflow file holds the right to publish under every name registered against it — reserving all four names against a single file would leave the reservations unconsumed, because that file only ever builds one distribution. Each reserved name therefore needs its own publish workflow file, and those files must exist before any pending publisher naming them is registered.**

4. **Publication is the last step of the release act, not a separate act.** The `release` skill gains the step after the GitHub Release is published: confirm the publish workflow ran, the version on the index equals the tag, the SHA-256 on the index equals the release note. A publication that did not happen is a release that is not finished; a release whose note does not exist is not published (the workflow already fires on the *published* release for this reason). **Amended by ADR-033 (accepted 2026-09-07), decision 2, which makes these last steps specific: tag → build once → attach the wheel and sdist to a draft GitHub Release → the founder reads the draft and publishes it → the publish job downloads and uploads those bytes. Publishing the draft is a human act by the founder, and it is also the approval GitHub will not sell us — required reviewers on a deployment environment are public-repository-only on this plan.**

5. **Downstream pins by version and hash, in an artifact that can hold a hash.** Orbis and Limen move from `git+…@vX.Y.Z` to `vitruvyan-motus==X.Y.Z` at the first re-pin after publication, and the hash travels in a **requirements or lock file installed under `--require-hashes`** — not in the dependency string. `--hash` is a requirements-file option and **not expressible in PEP 508**, so `pyproject.toml` and a Dockerfile `pip install vitruvyan-motus==X.Y.Z --hash=…` cannot carry it: `pyproject.toml` states the version constraint, the lock artifact beside it states the hash, and the install command names the lock artifact. A hash pin that is not installed with `--require-hashes` is decoration — the mode is what makes pip refuse the substituted wheel, and it applies to **every** requirement in the file, so the lock is complete or it does not run. An index is a public channel and Motus is evidence infrastructure; a pin that cannot notice a substituted wheel is not a pin. The hash in the pin is the hash in the release note (decision 2).

6. **The sold half never touches the index.** Perpetuum, Limen and any distribution that carries a level-6 or level-7 assertion are delivered through Vitruvyan's proprietary installer, under licence. Whether that installer is Vit with an authenticated channel is decided in orbis#31 and vitruvyan-packages#1, not here. What this ADR binds is the constraint: **nothing installed through the proprietary installer is ever needed to verify a receipt.** The open validator on the index verifies what the sold half produces, or the sold half is not sold.

7. **Continuous integration stays where the evidence is.** The characterisation workflows, the performance gate and the publication run on GitHub Actions in this repository. Jenkins is not attached to Motus. A release act split across two systems is a release act with two places to go wrong and one place to look.

8. **The repository becomes public at the first publication, or the ADR says why not.** The CTO's recommendation is that it does: the licence is already Apache-2.0, the README already writes to a stranger, and the contradiction in *Context* has no other resolution. If the founder decides otherwise, the reason is recorded here under *Accepted* and the README's links are rewritten so that none of them 404 for the reader.

## Consequences

- **What is given up.** The ability to correct a published version. PyPI does not let a version be re-uploaded; a wrong wheel is yanked and a new version released. This is the same discipline the tag already imposes (the release skill: never make the gate pass by retrying) and it now has an external witness.
- **What is accepted.** A public index answers `pip install vitruvyan-motus` for anyone, including people we have never spoken to; support and issues follow. The package's classifiers stay `Alpha` until 1.0.0 (ROADMAP), and the README says so.
- **What changes for the factory.** Every brief that touches packaging states the install story (motus#160, vitruvyan-packages#1); the packaging tests are the contract the index relies on and are edited under the same rule as `contract/` — with an ADR, not a convenience.
- **What does not change.** The release gate (ADR-006), the three characterisations (ADR-012), the note that states the cost (ADR-018). Publication cannot pass a gate that failed; it follows the release, it does not replace it.

## Alternatives rejected

- **Keep installing from git tags.** It works and it is what Orbis and Limen do today. It is rejected because it is not how Python software is installed by anybody else: a tag pin needs `git`, a network to GitHub and, for a private repository, a credential — three things a stranger evaluating the runtime should not need. It also leaves the two plugs uninstallable outside a checkout.
- **A private index (devpi, a Vitruvyan simple index) for everything.** Rejected for the open half because it puts a Vitruvyan endpoint between the reader and the validator, which ADR-021 decision 8 forbids. It remains a candidate transport for the sold half, inside the proprietary installer.
- **The paid half on PyPI too, licence-gated at runtime.** Rejected: an index is public by construction; a package that installs and refuses to run without a licence is a package whose refusal will be patched out, and it puts the sold assertion inside an artifact the seller does not control.
- **Publishing on the tag push instead of the published release.** Rejected in PR #72 for the reason it gives: a version on the index whose note does not exist yet is a version nobody can assess.
- **A single installer for both halves (Vit with an authenticated channel), recorded here as the CTO's proposal of 2026-09-07.** The founder chose PyPI for the open half. The proposal is not rejected for the sold half; it is deferred to orbis#31 and vitruvyan-packages#1 (decision 6).

## Hypotheses, labelled

- **H1.** Trusted Publishing works unchanged from a private repository, and continues to after the repository is made public. Falsified if the first `workflow_dispatch` run of PR #72's workflow fails at the upload step for a reason other than the missing PyPI configuration. **Replaced by ADR-033's H1 (accepted 2026-09-07): as written, this hypothesis proposed to test Trusted Publishing by dispatching the production workflow, which is the hole ADR-033 decision 1 closes. H1 is now tested against TestPyPI, with its own workflow file and its own publisher, and never by dispatching a production workflow.**
- **H2.** A `--require-hashes` lock artifact is workable in both consumers — a requirements file the Limen Dockerfile installs, and one beside Orbis' `pyproject.toml`. The cost it carries is that the mode is all-or-nothing: every transitive requirement needs its own hash, so each consumer gains a generated lock and the job that regenerates it. Falsified if either consumer cannot produce a complete lock at the first re-pin after publication — in which case the pin is `==X.Y.Z` plus a documented `pip download` check against the release note, the weaker thing, and this ADR is amended to say so rather than leaving the stronger claim standing.
